  ## Работа с системой контроля версий Git и GitHub в Visual Studio Code (пунтк 4)
Разобрался в функциях гитхаба через веб интерфейс https://github.com/

В рамках проекта настроена интеграция локальной среды разработки Visual Studio Code с удаленным репозиторием на GitHub. Для соблюдения требований к разработке операции фиксации версий осуществляются регулярно и небольшими логическими порциями с осмысленными описаниями коммитов.

### Управление через графический интерфейс (GUI) Visual Studio Code

В Visual Studio Code освоена встроенная панель управления версиями (**Source Control**, вызываемая сочетанием клавиш `Ctrl + Shift + G`)

* **Авторизация и связывание с GitHub:**
  * Подключение аккаунта GitHub выполнено через меню *Accounts* (иконка в левом нижнем углу IDE) с авторизацией через веб-интерфейс и протокол OAuth.
  * Настроен удаленный источник `origin`, указывающий на репозиторий проекта
* **Подготовка изменений (Staging):**
  * Отслеживание статуса файлов в блоке *Changes* (U — Untracked, M — Modified, D — Deleted).
  * Выборочное добавление файлов в индекс (Stage Changes) нажатием кнопки `+` рядом с файлом, либо добавление всех изменений сразу нажатием `+` у заголовка *Changes*.
* **Фиксация изменений (Commit):**
  * Ввод содержательного сообщения коммита в верхнее поле ввода в соответствии с соглашением Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`)
  * Фиксация коммита по нажатию комбинации `Ctrl + Enter` или синей кнопки **Commit**.
* **Синхронизация с удаленным репозиторием (Push / Pull / Fetch):**
  * Отправка локальных коммитов в удаленную ветку `main` на GitHub и получение изменений через кнопку **Sync Changes** в нижней статусной строке.
  * Выполнение расширенных действий (*Push to...*, *Pull from...*, *Fetch*) через меню троеточия `...` в заголовке панели Source Control.
* **Инспектирование изменений (Diff Viewer):**
  * Просмотр построчной разницы кода (диффов) перед коммитом по клику на любой файл из списка *Changes* (красный цвет — удаленные строки, зеленый — добавленные).
* **Управление ветками:**
  * Отображение текущей активной ветки в левом нижнем углу статусной строки.
  * Создание новых веток и переключение между ними через всплывающее меню палитры команд.

## Инструментарий и стек технологий для реализации проекта (пункт 3)

В соответствии с требованиями к проекту зафиксирован следующий набор инструментов и окружение разработки:

* **Операционная система:** Windows 11 Pro 
* **Среда разработки (IDE):** Visual Studio Code (с расширениями для работы с TypeScript, Vue, Docker и Git); для визуального администрирования и инспектирования базы данных используется DBeaver Community.
* **СУБД и способ развертывания:** PostgreSQL 17, разворачиваемая в изолированном контейнере Docker (Docker Desktop) через `docker-compose.yml` (рекомендованный способ для этапа разработки).
* **Инструмент проектирования схемы данных:** Draw.io (исходная схема ER-диаграммы размещена в `/docs/schema.drawio`, графическая копия — в `/docs/schema.png`).
* **Backend стек:** Node.js v22, фреймворк NestJS v10, драйвер `pg`, инструмент миграций `node-pg-migrate`, модуль авторизации `@nestjs/passport` (Passport Local Strategy), валидатор `joi`, хеширование паролей Argon2id.
* **Frontend стек:** Vue.js v3.5, сборщик Vite, UI-библиотека компонентов Quasar Framework.
* **Архитектурный протокол:** REST API для клиент-серверного взаимодействия.

## Проектирование схемы базы данных (ER-диаграмма)

В соответствии с требованиями первой недели была спроектирована и подготовлена схема базы данных для СУБД PostgreSQL.

### 1. Инструменты и формат реализации

* **Среда проектирования:** веб-редактор диаграмм **Draw.io** (входит в утвержденный стек проекта).
* **Метод построения:** диаграмма сгенерирована через встроенный инструмент **Mermaid ER-diagram** с последующей ручной калибровкой связей и оформления.
* **Размещение артефактов в проекте:**
  * Исходный файл схемы: `/docs/schema.drawio`
  * Графическая копия для быстрого просмотра: `/docs/schema.png`

### 2. Принципы и архитектурные решения схемы

1. **Двуязычное представление сущностей:**
   * Все таблицы и колонки названы на техническом английском языке (`snake_case`) для бесшовной интеграции с кодом бэкенда на NestJS и инструментом миграций `node-pg-migrate`.
   * Над каждым блоком таблицы добавлено явное наименование на русском языке в скобках (`(Организации)`, `(Отделы)`, `(Сотрудники)` и др.) для наглядности при проверке.
2. **Используемые типы данных:**
   * Первичные (`PK`) и внешние (`FK`) ключи спроектированы на базе типа `UUID`.
   * Даты и время фиксируются с учетом часовых поясов (`TIMESTAMPTZ` для `created_at`, `updated_at`, `deleted_at`).
   * Для окладов сотрудников (`salary`) выбран тип `NUMERIC(12, 2)` для исключения погрешностей округления.
   * Для хранения перечня изменившихся значений в аудите выбран формат `JSONB`.
3. **Реализация мягкого удаления (Soft Delete):**
   * В соответствии с ТЗ, во все основные таблицы добавлено поле `deleted_at (timestamptz)`. Записи при удалении не стираются физически, а помечаются датой удаления.
4. **Безопасность учетных записей:**
   * В таблице `USERS` предусмотрено поле `password_hash` для безопасного хранения паролей с использованием алгоритма хеширования Argon2id.

### 3. Состав спроектированных таблиц и связей

Схема покрывает все бизнес-сущности и требования технического задания:

* **ORGANIZATIONS (Организации):** справочник компаний с наименованием и комментариями.
* **DEPARTMENTS (Отделы):** поддерживает иерархическую древовидную структуру отделов через связь «родитель-потомок» (`parent_id` ссылается на `id` этой же таблицы) и внешнюю связь с организацией (`organization_id`).
* **POSITIONS (Должности):** справочник наименований должностей.
* **EMPLOYEES (Сотрудники):** анкетные данные, ФИО, дата рождения, паспортные реквизиты (серия, номер, код подразделения, кем и когда выдан) и структурированный адрес регистрации (область, населенный пункт, улица, дом, корпус, квартира).
* **FILES (Файлы) и EMPLOYEE_PASSPORT_FILES (Сканы паспортов):** учет загруженных файлов документов и реализация связи «многие-ко-многим» для прикрепления множественных сканов паспорта к сотруднику.
* **PERSONNEL_ACTIONS (Кадровые операции):** фиксация кадровых событий (прием на работу, изменение зарплаты, перевод в другой отдел, увольнение) с привязкой к сотруднику, отделу, должности и окладу.
* **USERS (Пользователи):** учетные записи с уникальным логином, хешем пароля Argon2id и ролевой моделью (`admin` / `hr_manager`).
* **AUDIT_LOGS (История изменений):** аудит всех значимых действий (кто изменил, когда, над какой сущностью и какие конкретно поля были изменены).
